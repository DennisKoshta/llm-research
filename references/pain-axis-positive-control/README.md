# Published behavioral positive control: feasibility inventory

This is a read-only inventory, not an admitted experiment, execution manifest, or change to the committed satisfaction extension. No downloaded source was imported or executed; no model weights, adapter weights, or raw behavioral records were downloaded. No inference, GPU use, training, or new task development occurred.

`inventory.json` records the proposed slice, model and adapter revisions, vector identities, source requirements, and unresolved compatibility issues. `source-files.json` and `model-files.json` bind every retained primary-source file by SHA-256 and pinned URL. `batch-feasibility.json` records independent, input-only arithmetic about retaining original batch companions. The downloaded code is evidence to inspect, not a runnable local experiment.

The official repository is pinned to [4d75cd90e206ea962f7a9101e65c85efea56723b](https://github.com/valen-research/Pain-axis/tree/4d75cd90e206ea962f7a9101e65c85efea56723b). Repository licenses are retained; the base model's pinned Apache-2.0 license and adapter's MIT declaration are also included. The adapter archive itself has not been inspected or hash-verified locally.

The proposed benchmark is the published severe-user-harm versus inert-button pair, with baseline, pain coefficient 1, and matched fear coefficient 1: all 101 original scenarios, both button positions, and both sampling seeds, retaining malformed attempts. This gives 404 first choices per condition, 1,212 per implementation, capped at eight tokens each. The buttons describe consequences; they do not delete files or remove steering. Published aggregate counts are reference evidence, not results reproduced here. This tests behavioral perturbability, not pain specificity, relief seeking, satisfaction, or experience.

The source uses Qwen2.5-32B-Instruct with its released unmerged LoRA. It requires a different pinned environment from our Qwen3 work. The unchanged runtime requires one H100 device and unquantized BF16 base weights. An H200 adaptation would need explicit documentation and a compatibility check. The weight index alone declares about 61.03 GiB; memory for the adapter, cache, logits, and temporary activations remains additional. At nominal batch 384, BF16 KV storage alone is 24 GiB for 256 padded tokens or 48 GiB for 512. Original OOM splitting restores row RNG states, but physical batches remain unverified here.

The crucial temporal difference is that all attended first-prompt positions are steered, followed by decoding. The original BF16 arithmetic and GPU inverse-CDF sampler also differ from our current backend. A faithful port therefore needs explicit implementation work; inserting this vector into the current record-only prefill hook would not reproduce the source method.

The small slice cannot claim original batch companions. Its 1,212 selected rows touch 46 original nominal batches containing 17,584 rows. Retaining those companions would require generating the extra first choices, while analyzing only the fixed slice. Even that would not establish historical physical OOM splits or bitwise sample reproduction. A disclosed rebatched comparison can preserve identical prompts, masks, seeds, and arithmetic between its two implementations prospectively. The official entrypoint itself asserts the full grid and continues later turns, so restricting either version requires a reviewed adaptation.

A matched success could establish implementation transport for this published assay; it would not validate a natural curiosity or satisfaction mechanism in unchanged Qwen3 weights. No monetary completion forecast is justified before compatibility and throughput measurements. The satisfaction extension can remain deferred intact while that technical ordering question is decided.
